# 恢复成功率基线（v0.1）

- 对应评审：R8（缺核心 KPI）、A5（缺测量协议）
- 状态：**协议已落地，样本仍是受控模拟窗口，不是真实应用矩阵**

## 为什么需要它

"恢复成功率"是本产品的核心卖点。没有测量协议，这个数字只能靠"跑一遍看看"，M1 的 go/no-go 门也就不存在。

## 当前协议

```
cargo run --manifest-path src-tauri/Cargo.toml -- --baseline 5
```

1. 创建 3 个受控模拟窗口：A（普通）、B（普通）、C（最大化）；
2. 捕获并建立工作空间（真实入库：workspaces / window_layouts / snapshots）；
3. 每轮用确定性偏移（`i*37 % 240`、`i*53 % 180`）破坏三个窗口的位置与显示状态；
4. 按工作空间恢复（`restore::apply`），逐窗口记录结果；
5. 写出 JSONL 明细 + 汇总。

### 判定

单个窗口算"通过"必须同时满足：

- `status == success`
- 位置/尺寸偏差 ≤ 8 px（跨 DPI 时 `max(8, 2×scale)`）
- `stateRestored == true`（最大化状态确实还原）

### 输出

JSONL 每行一个窗口：

```json
{"iteration":0,"target":"基线窗口 A","status":"success","code":null,
 "deltaPx":0,"stateRestored":true,"durationMs":161,"ok":true}
```

汇总给出：复核项数、通过数、成功率、错误码分布。门槛 95%，低于则进程退出码为 1（可接 CI）。


## 真实窗口基线（`--baseline-live`）

模拟窗口只能证明坐标换算对，证明不了真实应用。`--baseline-live N` 用**当前真实运行的窗口**做一次完整测量：

1. 扫描桌面，取前 N 个真实窗口（排除 WorkScene 自己）；
2. 建立工作空间（原始布局落库）；
3. 每个窗口按确定性偏移挪开（位置变、尺寸不变）；
4. 按工作空间恢复；
5. **独立复核**：不信任报告，自己再量一次矩形，算偏差。

### 这一跑直接抓出的缺陷

第一版跑出来是「独立测量 0px 全对，但报告 0 成功 / 4 失败」——原因是 `place_window` **用 `SetWindowPlacement` 的返回值判成败**。实测发现 Chromium 系窗口（Chrome / Electron / Antigravity / DeepSeek Harness）会返回 `FALSE`，但位置其实已经改了（`SetWindowPos` 生效）。

也就是说：**产品会把成功的恢复报成失败**，和"谎报成功"是同一类错误的镜像。已改为「API 只负责尝试，成败由实测偏差 + 显示状态判定」。

## 这个数字不能证明什么

- **样本是模拟窗口**：真实应用会自己改窗口大小（Chromium/Electron）、会有多进程、会有 UIPI 限制，这些都不在基线里；
- **只有单屏**：本机只有一台 3840×2160 @150%，跨屏与跨 DPI 未覆盖（真实基线同样只覆盖单屏）；\n- **真实窗口基线一次只有 4–9 个窗口**，且以 Chromium 系为主，缺少 Office / IDE / 终端类样本；
- **窗口数少**：3 个窗口不足以暴露"同一应用多窗口"的匹配压力。
