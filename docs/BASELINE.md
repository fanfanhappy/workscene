# 恢复成功率基线（v0.1）

- 对应评审：R8（缺核心 KPI）、A5（缺测量协议）
- 状态：**协议已落地，样本仍是受控模拟窗口，不是真实应用矩阵**

## 为什么需要它

"恢复成功率"是本产品的核心卖点。没有测量协议，这个数字只能靠"跑一遍看看"，M1 的 go/no-go 门也就不存在。

## 当前协议

```
cargo run --manifest-path src-tauri/Cargo.toml -- --baseline 5
```

1. 创建 3 个受控模拟窗口：A（普通）、B（普通）、C（最大化）；
2. 捕获并建立工作空间（真实入库：workspaces / window_layouts / snapshots）；
3. 每轮用确定性偏移（`i*37 % 240`、`i*53 % 180`）破坏三个窗口的位置与显示状态；
4. 按工作空间恢复（`restore::apply`），逐窗口记录结果；
5. 写出 JSONL 明细 + 汇总。

### 判定

单个窗口算"通过"必须同时满足：

- `status == success`
- 位置/尺寸偏差 ≤ 8 px（跨 DPI 时 `max(8, 2×scale)`）
- `stateRestored == true`（最大化状态确实还原）

### 输出

JSONL 每行一个窗口：

```json
{"iteration":0,"target":"基线窗口 A","status":"success","code":null,
 "deltaPx":0,"stateRestored":true,"durationMs":161,"ok":true}
```

汇总给出：复核项数、通过数、成功率、错误码分布。门槛 95%，低于则进程退出码为 1（可接 CI）。

## 最近一次结果（本机，2026-11-21）

```
[1/3] 工作空间就绪：3 个窗口，开始 5 轮恢复基线
[2/3] 复核项 15 个，通过 15 个，成功率 100.0%
[3/3] 错误码分布：{"ok": 15}
基线结果：PASS（门槛 95%，实际 100.0%）
```

## 这个数字不能证明什么

- **样本是模拟窗口**：真实应用会自己改窗口大小（Chromium/Electron）、会有多进程、会有 UIPI 限制，这些都不在基线里；
- **只有单屏**：本机只有一台 3840×2160 @150%，跨屏与跨 DPI 未覆盖；
- **窗口数少**：3 个窗口不足以暴露"同一应用多窗口"的匹配压力。

## 下一步（M3 收尾）

按评审 A5 的要求扩到：10 个应用（Notepad×2 / Chrome×3 / VS Code / Explorer×2 / Terminal / Excel / 一个 UWP 对照）× 3 场景（单屏同 DPI / 双屏同 DPI / 双屏 125%+150%），每场景输出同样的 JSONL，汇总成分场景成功率表。
