# WorkScene v1.0 产品需求与技术架构文档 — 评审意见

- 被评审文档：`WorkScene_Product_Requirements_and_Technical_Architecture_v1.0.docx`（v1.0，2026-11-21，宣称"正式设计基线"）
- 评审范围：全文 19 章 + 附录 A/B，含 58 张表格
- 评审日期：2026-11-21
- 评审视角：产品定位可行性、Windows 原生技术准确性、数据模型约束、需求可验收性、发布风险
- 结论摘要：**方向与架构判断正确，可作为开发基线；但"核心竞争力"缺少可度量的验收定义，窗口匹配与 DPI/显示器两大关键算法只有原则没有规格，数据模型有 12 处具体缺陷，需求与验收之间存在 4 处断链。建议按第 2 节 P0 项修订为 v1.1 后再进入 M1。**

## 1. 总体评价

| 维度 | 评价 | 说明 |
|---|---|---|
| 产品定位 | ★★★★☆ | "可验证、可诊断的现场恢复"切中 PowerToys Workspaces 的真空白；不做分屏是对的 |
| 技术路线 | ★★★★☆ | Tauri 2 + Rust + windows-rs + SQLite 与需求匹配；分层与约束清晰，无常见架构病 |
| 工程诚实度 | ★★★★★ | 主动声明"不能恢复应用内部状态""不默认提权""歧义时不操作"，这在同类文档里少见，是最大优点 |
| 需求可验收性 | ★★☆☆☆ | FR 有编号但验收条款多为定性描述；**核心卖点"恢复成功率"没有任何量化目标** |
| 关键算法规格 | ★★☆☆☆ | 窗口匹配评分、DPI 坐标换算、快照指纹均只有原则，无字段/权重/阈值/伪代码 |
| 数据模型 | ★★★☆☆ | 表覆盖完整，但有 12 处约束/索引/字段缺口，其中 4 处会导致功能无法实现 |
| 里程碑可信度 | ★★★☆☆ | 单人 9–11 周完成 M1–M6 偏乐观，且 M1 缺少量化 go/no-go 门 |
| 文档工程 | ★★★☆☆ | 缺 ADR、缺待决问题清单、缺 FR↔验收追溯矩阵；SQL/目录树/架构图塞在表格单元格里，后续必然腐化 |

一句话判断：**这是一份"想清楚了做什么、也说清了不能做什么"的文档，但还不是一份"能照着验收的"文档。** 差距集中在"把原则翻译成规格与指标"这一步。

## 2. 必须补的硬伤（P0，进 M1 前修）

### R1. 窗口匹配没有规格 —— 这是全产品的成败点，却只有一句话

文档 §4.2 FR-006、§7.2 只写了"组合进程路径、进程启动时间、类名、标题规则匹配；歧义时不操作"。这是**结论**，不是**设计**。M3 会卡在这里，且发布阻断条件第 1 条（"错误移动其他应用窗口"）正对应此处。

必须补齐：

1. **`WindowIdentity` 结构与评分表**：每个特征给出归一化方式与权重、门槛值。建议字段：exe 全路径哈希（权重最高）、进程启动时间（±2s 内视为同实例）、窗口类名、标题归一化后相似度、窗口矩形与目标的重合度、父窗口/所有者关系、适配器专属标识。
2. **歧义判定规则**：`top1_score > T_accept && (top1 - top2) > T_margin` 才允许操作；否则进入"提示用户选择 / 跳过"。必须给出 T_accept、T_margin 的具体初值与调参方法。
3. **标题归一化规则**：VS Code/Word/浏览器标题含文件名、项目名、`*` 未保存标记、`-` 分隔符、多语言前缀。要给正则归一化函数，而不是"标题规则"四个字。
4. **复用已有实例时如何区分多窗口**：`reuse_policy` 的枚举值（`reuse_if_matched` / `always_launch` / `reuse_or_launch`）在文档里只出现一个字符串，没有语义定义。这是 FR-005 与 FR-006 的交界，最易出 bug。
5. **可测试性**：把匹配引擎做成纯函数 + fixture 窗口集（含"两个一模一样的 Notepad""Chrome 三窗口""标题含未保存标记"等），否则这条红线无法回归。

### R2. DPI 与坐标空间只有公式，缺三个致命实现细节

§7.3 的归一化公式方向正确（值得肯定），但按当前描述实现，跨 DPI 场景会稳定地错位：

1. **WorkScene 自身必须是 Per-Monitor V2**（manifest + `SetProcessDpiAwarenessContext`），否则 `GetWindowRect` 返回的是被 DWM 虚拟化后的坐标，与"保存物理像素"自相矛盾。
2. **对目标窗口操作前需 `SetThreadDpiAwarenessContext`** 到与该窗口一致的 awareness context，否则在混 DPI 双屏上 `SetWindowPos` 的坐标语义不匹配，窗口会被二次缩放。
3. **验收阈值不能是固定 10 px**：§17 Day 4 的"约 10 px"只在同屏同 DPI 成立，文档也这么注明了，但缺跨 DPI 阈值。建议改为"窗口矩形与目标工作区域的比例偏差 ≤ 2%，且 ≤ max(16px, 2×scale)"，并按 100%/125%/150%/200% 四档分别给验收值。
4. 补 `WINDOWPLACEMENT.rcNormalPosition` 规则：**最小化/最大化窗口必须从 `rcNormalPosition` 取还原位置**，`GetWindowRect` 在最小化时返回 -32000 级别的无效值。这是最常见的实现陷阱，文档列了 API 却没写这条约束。
5. 补恢复顺序：最大化窗口需先 `SetWindowPlacement`（或先解除最大化再 `SetWindowPos`），否则 `SetWindowPos` 会静默解除最大化；跨屏最大化还需处理 `SW_MAXIMIZE` 的目标屏归属。

### R3. 缺少"窗口稳定"与"二次校正"机制 —— 10 px 目标会因此不达标

Chromium/Electron/Office 启动后会自行恢复上次窗口状态（Chrome 的 continue-where-you-left-off、VS Code 的窗口还原），把 WorkScene 刚设置的布局覆盖掉。文档 §7.1 只提到 `SetWinEventHook` 用于捕获，没有用于恢复后的校验。

建议补一节"恢复后收敛"：
- 设置位置后监听 `EVENT_OBJECT_LOCATIONCHANGE`，等待连续 500 ms 无变化视为稳定，再校验；
- 若漂移超过阈值，最多重试 2 次，之后记录 `layout_drift` 步骤状态并如实报告（不谎报成功）；
- 稳定判定失败的场景要写进恢复报告的 error_code 枚举。

### R4. 验收标准与需求存在断链（4 处）

§19 验收里有、但正文 FR 表/功能总表中没有来源的条目：

| 验收项 | 问题 |
|---|---|
| "支持工作空间导入与导出" | §4.2、§4.3 无对应 FR，且**导入 JSON 等于"一键执行任意程序"**，是安全面最大缺口（见 R5） |
| "异常退出后提供恢复提示" | 无 FR；也没有崩溃检测机制设计（心跳文件？`restore_runs` 未收尾判定？） |
| "提供本地数据管理和备份" | 无 FR；备份时机、位置、恢复流程均未定义 |
| "支持失败重试"（FR-013 提到） | 重试策略参数（次数、退避、哪些步骤可重试）未定义 |

反向也缺：§4.2 功能总表 16 行与 16 条 FR 之间没有显式映射（其中"智能化：工作空间推荐/自动分类（P2）"没有对应 FR），§19 也未按 FR 编号组织。**建议补一张 FR ↔ 验收标准 ↔ 里程碑 的三列追溯矩阵**，这是文档从"设计说明"升级为"验收基线"的关键一步。

### R5. 导入/导出的信任模型完全缺失（安全）

一旦支持导入工作空间，输入就是**不可信数据**：可指定任意 `executable_path` + 任意参数，用户点一次"恢复"即执行。§14.2 只有"未知可执行文件需用户确认"，没有针对导入的规则。必须补：

- 导入时**不自动执行、不自动恢复**，仅解析并展示差异；
- 导入清单中的可执行路径必须重新校验（签名者、路径是否在导入前已存在过、是否位于可移动介质/UNC）；
- 敏感字段（含用户路径、内网 URL）在导入预览中高亮；
- 明确拒绝导入"自动快照策略 + 开机自动恢复"组合（否则等于持久化后门）。

### R6. 快照指纹没有定义 —— FR-012 无法验收，且与"快速拖动窗口"直接冲突

§3.4、§8.5 反复强调"有意义变化才创建快照""指纹去重"，但**"有意义变化"没有定义**。若按窗口矩形精确比较，用户拖动窗口就会产生一条快照；若忽略矩形，移动窗口布局又不被记录。必须给出指纹字段与量化规则，例如：

- 窗口矩形按工作区宽高的 5% 分桶后参与指纹；
- z-order 不参与；标题不参与（标题含文档名，既抖动又泄露隐私）；仅参与 `identity_key` 集合；
- 指纹 = hash(排序后的 identity_key + monitor_key + 分桶矩形 + show_state)；
- 触发侧：事件去抖动窗口 10 s + 变化合并 30 s + 空闲优先。

同时补**保留策略的可执行定义**：手动快照永不自动淘汰；保护快照（恢复前自动创建）不参与淘汰；自动快照按"每工作空间保留 N 条 / 保留 N 天 / 总容量上限"三选一或组合，并规定淘汰顺序（先淘汰最旧自动快照，且不得破坏 `parent_snapshot_id` 链）。

### R7. 未覆盖的 Windows 现实场景（都会在 M1 立刻撞上）

文档把"不夸大能力"做得很好，但**漏掉的边界比夸大的边界更危险**，因为漏掉的会被默认当作已支持：

| 场景 | 现状 | 建议 |
|---|---|---|
| UWP / 打包应用 | §7.6 只说"需单独验证"，既未列入非目标也未进风险表 | v1 明确声明"不支持 UWP 窗口恢复"，或用 AUMID 启动 + 处理 `ApplicationFrameHost` 宿主窗口；二者选一写进 §2.3 |
| Windows 虚拟桌面（Task View） | 全文未提 | 至少声明为非目标；否则"重现现场"的验收会被用户按虚拟桌面理解 |
| 网络盘 / OneDrive 占位文件 / 符号链接 | 只有"路径存在性校验" | 补"资源可达性"矩阵：不存在 / 无权限 / 离线卷 / 云端仅占位（打开触发下载）/ 指向可移动介质；各给策略与 error_code |
| 盘符变化、目录被移动 | 只对"应用路径变化"提了重新定位 | 文件/项目也需重新定位：记录卷 GUID + 文件 ID（或卷序列号 + 相对路径），而非纯路径字符串 |
| WorkScene 自身多实例 | 未提 | 必须单实例（互斥量），否则两进程同时启动应用、抢窗口 |
| 并发恢复任务 | `restore_runs` 设计上可并发 | 明确"全局同时只允许 1 个恢复任务"，或按 workspace 加互斥 |
| 恢复时用户正在使用某窗口 | §13.6 只说"不强制关闭" | 补"尊重当前操作"规则：目标窗口处于前台且带未保存状态时，默认不移动，仅提示 |

### R8. 缺一个"恢复成功率"指标 —— 核心卖点无法度量

文档 §14.3 给了冷启动、列表、捕获、定位耗时等 9 个指标，唯独**没有产品自己的核心 KPI**。§5 明确说"核心竞争力应是恢复成功率"，却在验收里没有任何成功率目标。建议补：

| 指标 | 建议初值 | 测量方式 |
|---|---|---|
| 窗口布局恢复成功率 | ≥ 95%（单屏同 DPI） | 固定 10 应用 × 3 场景的脚本化基线 |
| 跨显示器/跨 DPI 成功率 | ≥ 85% | 双屏 + 125%/150% 组合矩阵 |
| **误移动率** | **必须 = 0** | 与红线一致，出现即阻断 |
| 应用启动成功率 | ≥ 98%（普通权限应用） | 排除 UAC 提权应用后统计 |
| 单工作空间恢复总耗时 | ≤ 30 s（10 应用） | 从 `restore_start` 到 `completed` |
| 自动快照日增量 | ≤ 20 条/天（典型使用） | 指纹去重效率的间接验证 |

这组数字同时应该成为 **M1 的 go/no-go 门**：若 5 应用场景恢复成功率 < 80%，则不是"继续完善 UI"，而是**重新评估产品定位**（例如退化为"应用启动器 + 布局预设"）。这个决策门目前文档没有。

## 3. 数据模型的具体缺陷（`§8.4` 迁移脚本逐条）

| # | 位置 | 问题 | 建议 |
|---|---|---|---|
| D1 | `workspaces` | §4.4 要求"封面"，表里只有 `icon`/`color` | 补 `cover` 或明确删除该需求 |
| D2 | `workspaces` | §4.4 要求"快照保留策略、敏感应用排除"，表里只有 `auto_snapshot_enabled` | 补 `snapshot_retention_json`、`excluded_json`，或明确改存 `app_settings` 并写进文档 |
| D3 | `snapshots.workspace_id` | `ON DELETE SET NULL` → 删除工作空间后，快照与全部 `snapshot_items` 变成**永久孤儿，无清理路径**，与"保留策略"矛盾 | 改为 `ON DELETE CASCADE`；若想保留历史，则加 `orphaned_at` 标记 + 明确的孤儿清理任务 |
| D4 | `snapshot_windows` | 只有 `process_key`，**没有回指 `workspace_item` 的键** → 从快照"恢复为工作空间"时窗口无法挂回资源项（§19 要求"历史查看和配置恢复"） | 补 `item_key TEXT`（稳定逻辑键）+ 索引 |
| D5 | `restore_steps` | 无 `seq`/`step_order` | 报告顺序依赖 `started_at`，同毫秒并发步骤会乱序；补 `seq INTEGER NOT NULL` + `UNIQUE(run_id, seq)` |
| D6 | `workspace_items` | 无 `UNIQUE(workspace_id, item_type, identity_key)` | 同一路径可被重复添加，恢复时重复打开；加唯一约束或明确规定允许重复 |
| D7 | 索引缺口 | `snapshot_windows`、`snapshot_displays` 无 `snapshot_id` 索引；`window_layouts` 缺 `(workspace_id,item_id)`；`snapshots` 缺 `content_fingerprint` 索引（指纹去重要查）；`audit_events` 缺 `(entity_type,entity_id)` | 补齐；`verifying` 阶段会按 snapshot_id 批量读 |
| D8 | `workspaces.schema_version` | 与 SQLx 的 `_sqlx_migrations` 重复，两套版本真源 | 删除该列，统一用 SQLx migration 版本；payload 版本保留在 `snapshots.payload_version` |
| D9 | `app_definitions.executable_path` | 无唯一性 | 同一 exe 可能出现两行，`app_key` 与路径不一致；加 `UNIQUE(executable_path)` |
| D10 | `workspace_items.target` | 单个 TEXT 混装 path / URL / 项目路径 | 补 `target_kind` 枚举或拆 `target_path`/`target_url`，并加 CHECK |
| D11 | `restore_runs` | 缺 `trigger_type`（手动/启动恢复/重试） | 恢复报告与审计需要区分来源 |
| D12 | `snapshots` | "快照不可变"只是约定，DB 层无任何保障 | 至少让 Repository 不暴露 update，补单测；如需强保证可加触发器拒绝对 `payload_json` 的 UPDATE |

另外，`§8.4` 把整段 DDL 放在表格单元格里（`<<TABLE 26>>`），实际文档中是一坨无换行的文本，**完全不可复制使用**。建议迁移到仓库 `src-tauri/migrations/0001_init.sql`，文档只保留表用途与关键约束清单。

## 4. 需求层面的缺漏（PRD 视角）

1. **没有"首次使用"设计**：捕获质量取决于系统窗口过滤，但文档没有过滤规则清单（`Progman`、`Shell_TrayWnd`、`Windows.UI.Core.CoreWindow`、输入法候选窗、任务栏缩略图等），也没定义首次运行引导（选常用应用、排除清单、自动快照开关、隐私说明）。这直接决定首启体验。
2. **缺"当前激活工作空间"概念**：自动快照要归属哪个工作空间？Dashboard 的"当前状态"指什么？没有 active workspace 模型，自动快照与切换语义都会含糊。
3. **缺冲突处理的默认策略**：目标显示器缺失时是自动回退还是询问？应用路径失效时是跳过还是弹重定位？文档只有"提示""回退"这类词，没有默认值，实现时会各写各的。
4. **浏览器行为矩阵缺失**：Chrome 已运行时 `--new-window <url>` 的复现行为、`--user-data-dir` 不同时的实例语义、Firefox 的参数差异，都决定"网址恢复"是成功还是部分成功。§11.4 只有原则。
5. **`z_order` 有字段无需求**：表里存了 z-order，需求与验收都没提"恢复叠放顺序"。要么删字段，要么补需求+验收（重叠窗口场景有意义）。
6. **P1 的系统集成（托盘、快捷键、开机启动）没有验收条款**，但 §19 又把它们列为发布项。
7. **缺卸载与数据保留策略**：卸载是否删库？升级失败是否回滚？`backups/` 目录何时写入？
8. **缺更新与签名**：只提"安装包"。对 Windows 产品，未签名 MSI/NSIS 会被 SmartScreen 拦截，Power User 也不会忍；且 Tauri 2 自带 updater 需要签名密钥管理。
9. **WebView2 依赖**：Windows 10 无内置 WebView2 运行时，安装包需 bootstrapper（`webview2-bootstrapper`）或声明依赖，否则首装白屏。
10. **竞品分析偏窄**：只列了 3 个（PowerToys Workspaces / DisplayFusion / Snap Groups），缺 Win11 原生"重启后恢复应用"（最直接竞品）、Mac 侧 Contexts（同类付费产品的定价参照）、Workspacer 等开源方案、以及浏览器/IDE 自带 session restore。PRD 需要回答"为什么付费而不免费用 PowerToys"，否则定位只是审美层面的差异化。

## 5. 架构与工程层面的建议

1. **DAG 是过度设计，建议改为固定三阶段流水线 + 资源依赖**。§9.3 用通用 DAG 编排，但实际依赖结构是固定的：`启动应用（并行，限并发）→ 匹配并定位窗口（串行）→ 打开资源/上下文（并行）`。通用 DAG 的收益在 v1 几乎为零，测试成本却很高。建议：先实现固定流水线，把 DAG 留给 L3 适配器按需插入依赖。文档同时要定义"缺省并发上限"（如 4）与"同应用实例串行"规则。
2. **长任务真源**：§10.6 已经写对（进度用 Channel，最终结果必须可 `restore_get_report` 拉取）。建议再补"UI 重启后如何重建进行中任务视图"（进程崩溃后 `restore_runs` 里非终态记录的处理）。
3. **单实例 + 全局互斥**（见 R7）。
4. **日志脱敏要落到实现约定**：§14.1 说"日志避免完整路径"，但 `tracing` 默认就会打路径。建议规定：路径记 hash 前缀 + 文件名，用户名替换为 `%USER%`，URL 记 host。否则隐私声明与实现会打架。
5. **CI 与 GUI 测试**：Windows 上的窗口操作集成测试需要真实交互式会话，GitHub Actions 的 windows runner 在非交互 session 下 `EnumWindows` 结果不可靠。建议明确：核心窗口逻辑用"抽象层 + 录制夹具"单测，真机验证走手工清单（Day 1–7 那种），别承诺 CI 全自动化。
6. **技术选型缺理由**：§1.1 是"正式决策"，但没有 rationale。为什么 Tauri 而非 WPF（原生 Win32 窗口操作更直接）？为什么 SQLite 而不是 JSON 文件（本可 v1 更简单）？建议补 ADR 或在决策表加"理由/替代方案"列，否则三个月后无法复盘。

## 6. 里程碑与排期评估

§16 的 M1–M6 合计 9–11 周（单人、理想情况）。按第 2 节列出的缺口，实际风险集中在：

| 里程碑 | 文档估算 | 评审判断 | 原因 |
|---|---|---|---|
| M1 系统能力验证 | 1 周 | 可信（前提是按 Day1–7 严格产出报告） | 范围收得好，有验收标准 |
| M2 基础工作空间 | 1–2 周 | 可信 | CRUD + 迁移，工作量线性 |
| M3 恢复引擎 | 2 周 | **偏乐观** | 匹配评分 + 等待/稳定/重试 + 跨 DPI 定位 + 报告，任一项都可能吃掉一周 |
| M4 上下文恢复 | 2 周 | 偏乐观 | 文件/网址 + VS Code/Terminal 适配，浏览器矩阵会反复 |
| M5 Hybrid 快照 | 2 周 | 中性 | 指纹规则一旦定死，实现不难；难的是"不多不少" |
| M6 专业体验 | 1–2 周 | **偏乐观** | 多显示器适配 + 托盘 + 快捷键 + 安装包 + 签名 + 更新器 |

建议：
- 把 M3 拆成 **M3a（单屏同 DPI 的启动→匹配→定位→报告）** 与 **M3b（多显示器 + 跨 DPI + 回退）**，各自独立验收；
- 给 M1 加**量化决策门**（见 R8）；
- 给 M6 单独列"发布工程"清单（签名、安装包、WebView2、更新器、卸载、崩溃恢复提示），这些不是"优化"，是独立工作量。
