## 三、问题清单

### P0-1 6964 行改动没有提交边界

`git status` 显示 30 个文件（+6964/−1903）全在工作区，其中前端是一整套 UI 重构、后端是 20 多个新命令。任何一次 `git checkout .`、`git stash`、或者另一路继续改写，都会让这批工作失去参照。

**建议**：立刻按"后端 / 前端 / 文档"拆成 3 个提交（或至少建一个 `feat/ui-v2` 分支提交），再继续开发。这也是后续 review、回滚、发布的前提。

### P0-2 导入工作空间不校验可执行路径（安全）

`data/workspaces.rs::import_json` 对 `apps[].target` 与 `launch_args` 原样入库，只做了：大小上限 2 MB、schema 版本、名称非空、应用/资源非空、应用去重。**没有校验 exe 是否存在、是否在可信位置**。

后果：把一份别人给的 JSON 导进来，点「恢复」就会按文件里的路径启动程序（参数按数组传给 `CreateProcess`，不会被 shell 注入，但**"导入即执行"的风险成立**）。前端导入成功后只弹一个 `toast.success("已导入「…」")`，没有任何风险提示。

正是一年前评审 R5 提的同一条，现在有了导入功能，它从"未实现所以不适用"变成了"已存在且未防护"。

**建议**（半天内可做完）：
1. 导入时逐个校验 `target`：不存在/不在常规安装目录/位于可移动介质 → 列入"可疑项"；
2. 导入确认弹窗列出"本文件将启动 N 个程序：…"，由用户显式确认；
3. 默认**剥离 `launch_args`**，或要求逐项确认后再保留；
4. 补一条单测：导入含不存在 exe 的 JSON 时应给出警告而不是静默成功。

### P1-3 `pnpm-workspace.yaml` 里有坏配置

```yaml
allowBuilds:
  esbuild: set this to true or false
```

`allowBuilds` 不是 pnpm 的合法键，值还是模板占位文字，看着像某次编辑没填完。它可能让 `pnpm install` 报错或忽略。**建议删除这两行**，保留 `onlyBuiltDependencies: [esbuild]`。

### P1-4 取消功能没有测试

`restore_cancel` / `is_cancelled` 只被 UI 与手动路径覆盖，没有单测或自检。取消后 run 归 `cancelled` 的映射逻辑（`runs.rs` 里按 `code=="cancelled"` 判定）也没有测试保护，后续改动容易悄悄退化成"取消却记成 completed"。

**建议**：补两条单测（取消后状态映射；取消不会把已成功步骤改成失败）。

### P2-1 枚举优化改变了"排除项"语义

`enumerate_visible` 在最早一步跳过不可见窗口，因此 `capture.excluded` 列表**不再包含不可见窗口**，只计入总数（"排除 N 个"仍准确）。这与 PRD §8.3"保留诊断信息"有偏差——是有意的性能取舍，但应在文档里写明。

### P2-2 复制工作空间不复制快照

`duplicate` 只复制 workspaces / items / app_configs / layouts，不复制 snapshots。好处是不会出现多工作空间共享同一 payload 文件的删除风险；但如果产品预期"复制含历史"，需要明确写进规格。

### P2-3 LayoutEditor 里的 macOS 风格残留

`LayoutEditor.tsx:511` 有注释"macOS 风格窗口模拟标题栏"。Windows 产品的视觉基线是 Fluent（UI 规范 §13），这类借鉴要么去掉，要么在规范里显式允许。
