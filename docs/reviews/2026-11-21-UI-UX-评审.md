# WorkScene v1.0 前端 UI/UX 设计规范 — 评审意见

- 被评审文档：`WorkScene_Frontend_UI_UX_Design_Guidelines_v1.0.docx`（v1.0，2026-11-21，宣称"前端设计基线 / 开发实施依据"）
- 评审范围：19 章 + 附录 A/B，56 张表格，**0 张图片**
- 对照文档：`WorkScene_Product_Requirements_and_Technical_Architecture_v1.0.docx`（同 v1.0，同日）
- 评审日期：2026-11-21
- 结论摘要：**信息架构与交互规则的文字部分质量很高（三态恢复、能力分级、不伪造进度几条尤其好），但作为"前端实施依据"缺三类东西：可看的界面（零图、线框不可读）、可查的断点与状态（组件状态、断点表、i18n 全缺）、可验的对照关系（与 PRD 有 6 处不一致，恢复状态机步数对不上）。另有 3 处色彩对比度经实测不达 WCAG AA，其中主按钮白字仅 3.05:1。**

---

## 1. 总体评价

| 维度 | 评价 | 说明 |
|---|---|---|
| 信息架构 | ★★★★☆ | 七个一级页面与三条主流程（Capture / Manage / Restore）清楚；详情页用 Tabs 分层正确 |
| 交互规则 | ★★★★☆ | "恢复前先预览、执行中可观察、执行后可诊断"贯穿全篇，不是口号，落到每页 |
| 诚实度 | ★★★★★ | 能力分级（Native/Adapter/Generic/Limited）明确禁止夸大；"不得用动画伪造进度""UI 不承诺后端没有的能力" |
| 可实施性 | ★★☆☆☆ | **零张视觉稿**，12 处 ASCII 线框在 Word 里被压成单行不可读；组件只有尺寸没有状态；断点、i18n、虚拟化全缺 |
| 设计系统 | ★★★☆☆ | Token 齐（色/字/间距/圆角/动效），但只有深色一套，浅色主题只有一句声明 |
| 与 PRD 一致性 | ★★★☆☆ | 大体对齐，但有 6 处结构性不一致（命名、导航层级、状态机步数、托盘缺失等） |
| 无障碍 | ★★★☆☆ | 原则达标（不只靠颜色、拖拽有替代、2px 焦点环），但缺键盘规格实体和 reduce-motion，且实测对比度有 3 处不达标 |
| 排期 | ★★★★☆ | UI-01～UI-10 顺序合理，"19.2 不建议的开发方式"这节很实用 |

一句话判断：**这是一份"交互想清楚了、但没法照着画"的设计规范。** 它的价值在文字规则，不在视觉交付；如果不补视觉稿与断点/状态规格，前端会各自发明界面，最终与文档无关。

## 2. 与 PRD 的交叉不一致（优先修，成本最低、危害最大）

两份文档同日同版本，应视为同一基线，但以下是**结构性**不一致：

| # | 位置 | 差异 | 建议 |
|---|---|---|---|
| X1 | UI §3.1 vs PRD §13.5 | 首页 PRD 叫 `Dashboard`，UI 叫 `Overview`（且 UI 正文 §5 标题写"Dashboard：Overview 工作环境总览"，一个标题里两种叫法） | 二选一，全局统一；建议 `Overview`（与"当前现场"语义更贴）或 `Dashboard`（用户更熟） |
| X2 | UI §3.1 vs PRD §13.5 | UI 把 `Applications` 提为一级导航；PRD 里它是 Settings 的一个分组。而 UI §12.1 的 Settings 里**仍有 Applications 分组** → 同一功能两个入口 | 保留一级导航，从 Settings 删除该组；或反之，但必须只有一个 |
| X3 | UI §3.3 vs PRD §12 | UI 把 Workspace Editor 作为 Workspaces 子页（正确）；PRD 页面清单让它与 Workspaces 平级 | 以 UI 为准，改 PRD |
| X4 | UI §9.2 计划步骤 5 步 vs PRD §4.5 状态机 8 阶段 | UI："Check displays → Launch apps → Restore windows → Open resources → Verify"；PRD：`Pending→Validating→Planning→Launching→WaitingWindow→Positioning→RestoringContext→Verifying`。**用户看到的进度条会被后端 8 个阶段推进，但文案按 5 步写**，必然出现"步骤 3/5 但状态是 Positioning"这类错位 | 补一张"后端阶段 → 用户可见步骤"的映射表（建议 8→5 折叠，WaitingWindow 并入 Launching、Positioning 并入 Restore windows），并明确 `totalSteps` 由谁给 |
| X5 | UI 全文 vs PRD FR-016 | **系统托盘与全局快捷键没有界面规格**：没有托盘图标、托盘菜单结构（快速恢复 / 暂停自动快照 / 打开主窗口 / 退出）、托盘状态（捕获中/恢复中）设计。而 PRD §19 把"提供系统托盘与快捷键"列为发布验收项 | 补 §16.x 托盘规格；这是 Windows 桌面产品的高频入口，不能只有 Settings 里的一个开关 |
| X6 | UI §14.2 vs PRD 全文 | UI 的 "Suggested Action"（"Map windows from Display 2 to the primary display" / "Skip Photoshop and continue"）需要后端生成建议文案与映射计划；PRD 中没有"suggested action"这一概念，FR 表里也没有 | 要么在 PRD 补 FR（建议引擎），要么 UI 改为只展示静态规则文案（"目标显示器缺失，将映射到主显示器"） |

另外两处**字段级**不一致，与上一份 PRD 评审的 D1/D2 完全对应（可交叉验证）：

- UI §8.6 的 `Category / Tags`，PRD 的 `workspaces` 表没有 category/tag 字段；
- UI §6.2 卡片要显示"封面"级别信息（PRD §4.4 明确要求"封面"），PRD 表里也没有 cover 字段。
→ 说明这两项需求**在两次文档里都被写进需求、都没进数据模型**，最可能是已经事实上放弃。建议正式从 PRD §4.4 删除，别留给实现时猜。

## 3. 必须补的缺口（P0，进前端开发前）

### U1. 视觉交付物为零 —— "设计规范"没有任何一张图

文档 `inline_shapes = 0`，全篇 56 张表，其中 **11 张表里塞的是 ASCII 框线字符**（9 张线框 + 2 张目录树，分别为 §4.1、§5.3、§6.3、§7.2、§7.5、§8.2、§9.2、§10.3、§13.3 及 §3.3、§18 的目录树）。这些线框写在表格单元格里，Word 用比例字体折行渲染，实际效果是**一坨无法分辨的框线字符**（本次提取所见即如此）。同时 §15 给了 12 个色值、7 档字号，却没有一张真实界面。

后果很具体：前端拿不到"卡片长什么样""Inspector 多宽""空状态怎么排版"，只能自由发挥；而文档又要求"统一圆角、统一间距、不硬编码颜色"——**没有视觉稿时，这些规则没有施加对象**。

建议（二选一，成本都不高）：
1. **补 3 张高保真关键页**：Overview、Restore Center（Running 态）、Visual Workspace Map。一张关键页胜过十页文字，且能定死间距与密度；
2. 线框改为**等宽字体 + 独立横向页面 + 不折行**（或直接放图片），至少让现有 12 处线框可读。

同时把"本规范为结构示意、非像素级视觉稿"这句话保留在文档控制里 —— 这个自我限定是诚实的，但它意味着**这份文档目前只能算交互规范，不能算设计规范**，命名与验收标准应跟着改。

### U2. 浅色主题只有一句声明，没有 token

§2.3 说"支持浅色主题与跟随系统"，§附录 A 验收要求"主题切换覆盖全部页面和弹窗"，但 §15.1 只给了一套深色 Token。**没有 Light 色板，"覆盖全部页面"这条验收无法执行。** 建议补 Light 的 12 个 token（背景/Surface/Border/Text×3/状态色），并说明 Light 下 Primary 是否换色（深色背景上的 #6C8FF5 在浅色下对比度不足，必须换）。

### U3. 色彩对比度实测 3 处不达标（可验证的数字）

用 WCAG 2.1 相对亮度公式实算（非目测）：

| 组合 | 实测 | 要求 | 结论 |
|---|---|---|---|
| 白字 `#FFFFFF` on Primary `#6C8FF5`（主按钮） | **3.05:1** | 正文 4.5:1（大字 3:1） | **不达标**。主按钮是最高频元素，白字落在 13px 上必挂 |
| Text Muted `#748196` on Surface `#1B222C` | **4.06:1** | 4.5:1 | 不达标（且它专门用于 11px 辅助文字，字号越小要求越严） |
| Border `#303A47` vs Surface `#1B222C` | **1.39:1** | 非文本 3:1（1.4.11，当边框是控件唯一视觉边界时） | 不达标。Input 用了 Border 作唯一边界 |
| Text Secondary `#98A4B4` on Surface | 6.33:1 | 4.5:1 | 通过 |
| Success/Warning/Danger on Background | 7.30 / 9.35 / 5.93 | 4.5:1 | 通过 |
| Text Primary `#EDF1F7` on Background | 16.42:1 | 4.5:1 | 通过 |

修法（已验算）：
- 主按钮二选一：文字改深色 `#101318` on `#6C8FF5` = **6.10:1**（推荐，且更像 Linear）；或配色加深到 `#4A66CC`，白字 = **5.17:1**。
- Text Muted 提到 `#828FA3`（on Surface = **4.88:1**）。
- 控件边框提到 `#6B7482`（vs Surface = **3.39:1**）；纯装饰分割线可继续用 `#303A47`，但要在文档里区分"分割线"与"控件边框"两种 token。

### U4. 组件只有尺寸，没有状态矩阵与表单规范

§15.7 给了 Button/Card/Dialog/Badge/Tooltip/Toast 的高低与圆角，但没有：
- 每个组件的 **default / hover / active / focus / disabled / loading / error** 七态视觉与文案；
- **表单校验规范**（错误文案位置、必填标识、字段级 vs 页面级错误、异步校验时机）——全篇只有 §16.2 一句"表单错误贴近对应字段"；
- **数据表格规范**（List 视图要用：行高 40/44px？斑马纹？列宽策略？排序指示？空列？截断与 Tooltip）；
- **拖拽状态**（拖起、落点提示、禁止放置、多选拖拽）。

没有这些，Design System 会退化成"一堆色值和字号"，组件仍各写各的。

### U5. Visual Workspace Map 缺核心几何规格 —— 而它是最有辨识度的界面

§7.4 给了 7 个组件，但**所有实现必需的量都没定义**：

- **坐标系**：画布 px ↔ 物理像素 ↔ DIP 的换算关系；画布缩放范围（50%–400%？）；显示器负坐标（左侧副屏 x = -1920）如何排布；不同 DPI 显示器如何在同一画布上保持"物理比例"（24" 125% 与 27" 100% 的实际 cm 比例 vs 像素比例）。
- **吸附规则**：边对齐/中线对齐/同尺寸吸附的触发阈值（8px？）；是否吸其他窗口、是否吸显示器工作区边界。
- **键盘编辑**：方向键步长（1px/Shift 10px）、Tab 在窗口间切换、拖动中 Esc 取消。
- **超出画布的显示器**：小地图/缩略导航 or 自动 Fit。
- **比例坐标的双向换算**：PRD 存的是 `x_ratio`（相对工作区），画布编辑的是像素；显示器尺寸变化后两者如何互转，必须写清楚，否则用户拖动后的坐标与恢复时的坐标会不一致。
- **多窗口重叠时的选择**（点击命中哪个窗口 Tile）、**z-order 编辑**（PRD 表里有 `z_order` 字段但需求没写，见 PRD 评审）。

这是"单独做技术 Spike"（§19.1）的对象，但 Spike 前必须先把上面 6 条写成规格，否则 Spike 输出的是一堆待决问题。

### U6. 窗口匹配规则的编辑器完全没有形态

PRD 把"窗口匹配"列为发布阻断条件 #1，UI §7.4 的 Inspector 只列了"Matching Rule"四个字，§12.1 的 Restore Rules 只有"复用策略"一行。**产品最难、最容易出错的一块 UI 是空白**：用户如何看懂"这个窗口是靠什么被识别的"？如何调整标题规则？歧义时如何选择候选窗口？

建议补：
- Inspector 里"识别依据"以**只读卡片**呈现（可执行文件名、类名、标题规则、上次匹配结果），默认不可编辑；
- 高级模式才允许改标题正则，且提供"用当前窗口测试"；
- 歧义场景的**候选窗口选择器**（带缩略图/路径/启动时间），这是 §8.5"应展示可区分信息"真正要落地的组件。

### U7. 缺"恢复不打断用户"的硬要求 —— 这是会被卸载的原因

恢复过程的本质是**批量移动用户正在使用的窗口**。全篇没有一条规则约束"不要抢焦点、不要强制置顶、不要切换虚拟桌面、不要在用户键入时移动窗口"。§9.3 只说"任务切换到后台后仍可找回状态"。

必须在交互规范里写死：
- 恢复期间的 `SetWindowPos` 必须带 `SWP_NOACTIVATE`（不激活）；**不得改变前台窗口**；
- 恢复前若检测到前台窗口属于恢复目标且处于编辑状态，默认延后或提示（PRD 评审 R7 的同类问题）；
- 提供"静默恢复"模式（默认开）：不弹窗、不抢焦点，仅托盘进度；
- 恢复中用户手动拖动窗口的行为要定义（视为用户意图，后端的二次校正跳过该窗口 —— 与 PRD 评审 R3 的"收敛重试"必须联动）。

### U8. 断点表缺失，且与"最小宽度 1000px"矛盾

§4.2 说最小窗口宽 ~1000px，§4.4 说"变窄优先收 Inspector、再折叠导航"，但没有给出**具体断点**。前端无法实现。建议给 3 个断点：≥1440（三栏）、1100–1440（收 Inspector）、<1100（折叠导航至 64px）。同时明确：既然最小 1000px，"折叠态"只用于手动拉窄，还是允许更窄（如 860px）？现在这两种读法都成立。

### U9. 数据量上限与虚拟化没有规格

PRD 压力测试明确"500 个自动快照、100 个窗口、20 个应用"。UI 的 History 时间线、Workspaces 列表、Capture 的窗口清单都没有提虚拟滚动/分页/加载更多。500 条 DOM 在 Tauri WebView2 里滚动会明显掉帧。建议：列表统一虚拟化（阈值 >50 条）、History 按天分组 + 懒加载、Compare 页最多展开 N 条差异。

### U10. i18n 未决策，而界面文案全是英文

正文中文、界面文案英文（"Your workspace, ready when you are." "Capture Current Setup"）。§12.1 General 有"语言"设置，但全篇没有：
- v1 是否只发英文 UI？（若目标是中文 Power User，这是产品决策不是实现细节）
- 文案表在哪（现在散落在 12 处线框里，无法维护）；
- 中英长度差异对按钮/导航的影响（"Restore" vs "恢复"，"Restore Center" vs "恢复中心"）；
- 日期/时间/路径的本地化格式。

建议：先把 UI 文案抽成 `en-US` + `zh-CN` 两份 key 表（哪怕 zh-CN 先留空），否则后期改文案要动 JSX。

## 4. 次级问题（不阻塞，但会被用户感知）

| # | 问题 | 说明 / 建议 |
|---|---|---|
| S1 | 中文 11px 偏小 | §15.2 辅助文字 11px、正文 13px。西文可接受，中文在 100% 缩放下 11px 明显吃力（笔画挤在一起）。建议中文最小 12px，并把"11px"限定给英文/数字标签 |
| S2 | 动效缺 reduce-motion | §15.6 全是 120–200ms 过渡，但没写"跟随 Windows 设置 → 辅助功能 → 显示动画关闭时，全部过渡降为 0ms"。§17 无障碍也没提 |
| S3 | 缺完整快捷键表 | §13.1 说"默认值在工程阶段验证"，§17 说"快捷键在界面中展示"，但没有任何一张表。Power User 产品的快捷键是需求，不是细节：至少给 10 个核心键（唤起面板、捕获、恢复、切页、搜索）与冲突检测规则 |
| S4 | Capture 缺窗口缩略图 | §8.4 只列标题/进程/状态。用户面对"三个同名 Chrome 窗口"时，**文字无法区分**。这是捕获体验的关键缺口，也是"避免误选"的真实手段（DWM 缩略图或截图，成本不高） |
| S5 | 空状态只有文字 | §16.4 五类空状态都靠文案 + CTA，没有插画/示意图资源规划。而产品定位是"专业级"，首次使用页的观感直接决定留存 |
| S6 | Toast 与报告的关系 | §16.2"重要错误必须保留在任务详情中"方向对，但没说 Toast 的停留时长、是否可撤销（Undo）、并发多条怎么堆叠 |
| S7 | 恢复预览默认"可跳过" | §5.4 允许"跳过预览"，但默认保留预览。建议加约束：**首次使用、显示器变化、存在 Warning 时强制预览**，否则用户会关掉唯一的安全网 |
| S8 | 侧边栏折叠后的信息损失 | §3.2 折叠为图标栏，但 "Restore Center / History" 等图标语义接近，需规定 Tooltip 文案与选中态样式 |
| S9 | 附录 A 验收清单不可验收 | "布局没有严重溢出""失败原因可读"是主观表述。建议改成布尔或数值条件（如"1000px 宽下无横向滚动条""错误码 + 建议动作两项均非空"） |
| S10 | Workspace Editor 的"未保存修改"语义 | §7.6 说"离开页面提示保存"，但没定义自动保存/草稿/撤销栈深度。Editor 是重配置页，用户丢一次配置就不再信任 |

## 5. 做得对、建议保留的（避免后续修订时被改坏）

1. **三态恢复中心 + "不要只显示 100%"**（§9.4）：把"部分成功"作为一等公民，是全文最专业的一条。配合"不得用动画伪造进度"，等于给产品立了诚实条款。
2. **能力分级 UI 明确禁止夸大**（§11.2、§11.4"Generic 应用不应显示为 Adapter"）：与后端"不夸大恢复能力"原则闭环，跨文档一致性的正面案例。
3. **§19.2 不建议的开发方式**：五条都是真实会犯的错（先做空壳、每页自己定义颜色、前端假造进度、把 Map 做成静态图、按钮提前标可用）。建议把这一节前置到文档开头，写代码的人未必读到第 19 章。
4. **§7.7 与附录 B 的边界声明**：画布不改显示器物理排列、Command Palette 不做自然语言、v1 不做 AI。把"未来"从"现在"里切出来，避免了最常见的需求膨胀。
5. **拖拽有键盘/Inspector 替代**（§17）：很多产品做不到，这条应该保留并写进组件验收。

## 6. 排期与优先级

§19 的 UI-01～UI-10 顺序基本正确，但有一处**优先级错判**：

> UI-06 Visual Workspace Map 标为 P1，理由"需与窗口恢复引擎联调"。

问题在于：**Map 的只读形态是 P0 依赖** —— Capture 的 Step 3（§8.5"使用 Visual Workspace Map 预览捕获到的布局"）和 Restore Preview（§9.2 显示器缺失映射预览）都需要它。把整个 Map 推到 P1，会导致 Capture 向导和恢复预览在 UI-04/UI-05 阶段没有布局可视化可用。

建议拆分：
- **UI-06a 只读画布（渲染显示器 + 窗口矩形 + 缺失显示器回退预览）→ 提到 P0，排在 UI-04 之前**；
- **UI-06b 可编辑画布（拖拽/缩放/吸附/撤销）→ 保持 P1**。

另外 §19.1 节奏里"用静态 Mock Data 完成高保真原型"是对的，但既然文档本身没有视觉稿（U1），这一步不做完之前，UI-01 的 Design System 无法"先固定视觉语言"。**建议把"3 张高保真关键页"作为 UI-01 的前置交付物。**
