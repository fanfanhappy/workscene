## 1. 两份评审的共同盲区（均未覆盖，建议补进基线）

### A1. 缺第三个评审对象：代码已经先行落地，与 PRD 架构分叉

时间线本身就说明问题：两份评审 15:38 / 15:49 定稿，代码 15:52 开始写。结论是"先改文档到 v1.1 再进 M1"，实际走的是"先写 M1 竖切"。于是出现分叉：

| PRD v1.0 的架构 | 代码实际 |
|---|---|
| SQLite + SQLx + 12 张表 + `migrations/0001_init.sql` | `%LOCALAPPDATA%\WorkScene\snapshots\scene-*.json`，`Cargo.toml` 无 sqlx，仓库无 `*.sql` |
| `workspaces` / `workspace_items` / `app_definitions` / `snapshots` / `snapshot_windows` / `restore_runs` / `restore_steps` / `audit_events` | 只有 `SceneFile { displays, windows }` 一份 JSON |
| 文件 / URL / 项目上下文恢复（FR-008/009） | 模型里没有 target 概念，v1 只恢复"窗口在哪" |
| 恢复运行可 `restore_get_report` 回查 | 报告是 `restore_apply` 的返回值，进程内即焚 |

这不是"实现没跟上文档"，而是**架构决策被静默替换**。R 评审 §5.6 已经要求补 ADR，现在这条从"建议"升级为"阻塞项"：必须先落一份 `docs/adr/0001-file-storage-instead-of-sqlite.md`，说明为什么 v1 用文件、12 表模型是延后还是废弃、`identity_key` / `snapshot` 语义在文件形态下如何承载。否则 R 评审第 3 节的 D1–D12（级联删除、孤儿清理、`seq`、唯一约束、指纹索引）**修完文档也没有落点**，纯属消耗。

顺带：D8 指出"两套 schema 真源"，文件形态下这个问题变成了 `SceneFile.schema_version` 与 `_sqlx_migrations` 都不存在——版本真源现在是一个裸整数，`load_scene` 只做"大于当前版本就报错"，没有迁移函数、没有反向兼容测试。

### A2. 快照落盘的隐私面：两份评审只审了"日志脱敏"

R 评审 §5.4 要求日志脱敏（路径、用户名、URL host），U 评审没有任何隐私条款。但真正敏感的是**快照文件本身**：`SceneWindow.title` 是明文窗口标题（`Q3 财报-终稿.xlsx - Excel`、`admin@internal.corp - 登录 - Chrome`），`process_path` 是明文完整路径，`displays` 是完整设备布局。这份文件躺在用户可写的 `%LOCALAPPDATA%`，可被同机任何进程读取、被用户随手发给同事做"排障"。

建议补三条（成本都很低）：

1. **落盘分级**：默认存 `title_hash` + 可选明文标题（默认开，但导出时默认剥离）；路径按"盘符 + 相对路径 + 卷序列哈希"存，不存完整字符串；
2. **导出脱敏**：R 评审 R5 只管"导入不可信"，漏了"导出会泄密"——导出预览必须显示"本次将带出 N 个窗口标题、M 条完整路径"；
3. **静态加密**：至少对 `snapshots/` 加 DPAPI（当前用户）保护，并在 PRD 隐私节写明"未加密时文件可被同机进程读取"这句实话——这与产品整体的诚实定位一致。

U 评审附录 A 的验收清单里也没有"快照文件不含明文敏感信息"这一条，建议加入。

### A3. 文件存储下"快照不可变"要换一套语义，评审的 D12 不适用

R 评审 D12 的解法是"Repository 不暴露 update，或触发器拒绝对 payload_json 的 UPDATE"。文件形态下这条失效，而真正的风险变成三个：

1. **写入非原子**：`storage::save_scene` 直接 `std::fs::write`（`storage/mod.rs:114`）。写到一半崩溃/断电 → 半个 JSON；
2. **损坏静默降级**：`list_scenes` 对解析失败的文件 `continue`（`storage/mod.rs:142-144`），用户看到的是"快照凭空消失"，没有任何提示；
3. **无备份、无回滚**：卸载、升级、误删都不可逆，PRD 里"提供本地数据管理和备份"仍是空头需求（R 评审 R4 已指出无 FR）。

修法：写 `*.json.tmp` → `rename` → 保留一份 `*.bak`；`list_scenes` 收集损坏文件并在 UI 上给"1 个快照损坏（可尝试修复）"的诊断项；每次 `restore_apply` 前自动写一份"恢复前"快照（这也是下面 A8 撤销功能的数据基础）。

### A4. 缺一份"恢复契约"：error_code、报告 schema、每状态的用户文案

R 评审给了 `restore_runs` 表，U 评审给了三态恢复中心，两边都假设中间有个**报告契约**，但谁都没写。现实是 `StepStatus` 只有 5 个值（`Success/Failed/Skipped/Timeout/NeedsReview`），`message` 是自由中文句子（`restore/mod.rs:282-321`）。

后果很具体：

- 无法做"可诊断"——用户拿到的是句子，无法按错误聚合、无法给"建议动作"；
- 无法做验收统计——R8 的成功率指标需要按 `code` 归类，句子没法统计；
- 无法做 U 评审 X4 的阶段映射——报告里根本没有"阶段"这一层。

建议补 `docs/RESTORE_CONTRACT.md`：`error_code` 枚举（`match_ambiguous` / `exe_missing` / `exe_relocated` / `uipi_denied` / `window_vanished` / `layout_drift` / `state_not_restored` / `launch_timeout` …）、每条 code 的 `user_message` + `suggested_action` + `severity`、`RestoreReport` 的 JSON schema、以及"什么算 Success"的判定表。这一页同时是后端、UI 文案、验收脚本三方的唯一交点。

### A5. R8 给了指标，没给测量协议

"恢复成功率 ≥95%"没有定义"怎么算成功"。当前实现里连"成功"都不可靠（见 D1）。建议直接复用已有的 `--selftest` 出口（`lib.rs:30`）做基线格式：

- 固定 10 个应用（Notepad×2 / Chrome×3 / VS Code / Explorer×2 / Terminal / Excel / 一个 UWP 对照）；
- 3 个场景（单屏同 DPI / 双屏同 DPI / 双屏 125%+150%）；
- 每次恢复输出 `{scene, expected, actual, per_step_status, delta_px, elapsed_ms}` 的 JSONL；
- 成功率判定 = `status==success && 位置偏差 ≤ 阈值 && show_state==期望`。

没有这一层，R8 的数字只能靠"跑一遍看看"，M1 的 go/no-go 门也就没有门。

### A6. 商业可行性仍然无人评审

R 评审自己声明未评品牌/定价/商业模式。但"为什么付费而不免费用 PowerToys Workspaces / Win11 原生重启恢复"这个问题不解决，前面所有技术评审的边际价值都会被质疑。建议把 M1 决策门加一条定性门：10 个目标用户中 ≥3 人明确表示"愿意为可诊断的恢复报告/历史快照付费"，否则退化为"布局预设 + 启动器"（R 评审 §8 已提，但没有落到 M1 门里）。

### A7. Windows 会话层：两份文档都只假设"单用户、交互式、Explorer 已就绪"

以下场景在 Power User 设备上很常见，且都会让"恢复"给出一堆假失败：

| 场景 | 当前会发生什么 |
|---|---|
| RDP 连接/断开、锁屏 | `EnumWindows` 结果变化，窗口可能被重排；恢复在后台跑一半 |
| 快速用户切换 / 多用户 | `%LOCALAPPDATA%` 隔离是对的，但"开机自动恢复"可能在其他用户会话触发 |
| 开机恢复时序 | 启动时 Explorer/`StartMenuExperienceHost` 尚未就绪，`Shell_TrayWnd` 出现前后工作区尺寸不同 |
| UAC 提权窗口、UIPI | `SetWindowPos/SetWindowPlacement` 静默失败 → 当前被判 `Failed`，文案是"可能受 UIPI 限制"，但报告里没有可区分的 code |
| 虚拟桌面（Task View） | 只在当前桌面枚举，行为"看起来成功了但窗口在别的桌面" |

建议在 PRD 加一节"会话与时机"，至少把 RDP/锁屏/开机时序列为"v1 best-effort + 明确提示"，并把 UIPI 失败识别成独立 error_code 而不是字符串猜测。

### A8. 缺"可回退"：恢复前保护快照 + 一键撤销

U 评审 U7 讲"恢复不打断用户"，R 评审讲"不强制关闭"，但两份都没讲**恢复做错了怎么撤**。批量移动窗口是本产品风险最高的动作，而当前 UI 只有"再次恢复 / 返回预览"（`Restore.tsx:313-327`），没有撤销。

建议：`restore_apply` 前自动 `scene_save("恢复前 HH:MM")`（复用现有存储，1 小时工作量），报告页给"撤销这次恢复"（把该快照再 apply 一次），并在保留策略里把这类快照标为"保护快照不参与淘汰"——正好把 R 评审 R6 里那条悬空的"保护快照"需求落地。

## 4. 代码中评审看不见、但会直接打脸"诚实原则"的缺陷

### D1（P0，谎报成功）`apply_placement` 里 `GetWindowPlacement` 把所有字段覆盖回当前值

`window.rs:123-152` 的顺序是：先填 `showCmd` / `ptMinPosition` / `ptMaxPosition` / `rcNormalPosition`，**然后**调 `GetWindowPlacement(hwnd, &mut wp)`，再只重设 `rcNormalPosition`，最后 `SetWindowPlacement`。

`GetWindowPlacement` 会写回 `showCmd`、`flags`、`ptMinPosition`、`ptMaxPosition`、`rcNormalPosition` —— 也就是说传进去的 `SW_SHOWMAXIMIZED` 被丢弃，`showCmd` 变成窗口**当前**状态。

后果：一个当前是 Normal 的窗口（新启动的应用窗口都是），即使快照里是最大化，恢复后仍然是 Normal；而 `place_window` 之前已 `SetWindowPos` 到目标矩形，`verify` 只比 `left/top` 且容差 8px → **delta≈0 → 报 `Success`**，文案还写"已最大化到目标显示器"（`restore/mod.rs:312-314`）。

这是当前代码里最严重的一条：**产品在最核心的诚实条款上撒了谎**，而且只在"应用重启后恢复"这个主场景触发。修法：把 `GetWindowPlacement` 挪到赋值之前（或干脆不读，只构造后 `SetWindowPlacement`），并对最大化单独校验 `IsZoomed(hwnd) != 0`。

### D2（P0，语义错）最小化窗口被静默恢复为可见窗口，报告不披露

`place_window` 有意把 `Minimized` 归到 `Normal`（`restore/mod.rs:401-404`，注释理由是"用户看不到窗口会以为失败"）——这个取舍可以接受，但**报告里没有任何字段说明"显示状态未还原"**。用户看到的是"成功"，实际与快照不同。建议 `RestoreStepResult` 增加 `state_restored: bool`，状态码 `state_not_restored`，文案写"已恢复到目标位置；原快照中该窗口为最小化，为避免误解已还原为普通窗口"。

### D3（P1，会移动错窗口）匹配器不消耗候选，且 `needs_launch` 只看"同 exe 是否存在"

- `apply` 每个窗口都拿**全量**候选重新打分（`restore/mod.rs:272`），同一个 `hwnd` 可能被两个目标先后选中：窗口 A 被移动两次，窗口 B 的布局丢失，报告却显示 2 个 Success。修法：run 内维护 `used: HashSet<hwnd>`，已用候选从池中移除。
- `needs_launch` 判定为"当前存在同 `process_path` 的任意窗口"（`restore/mod.rs:253-259`），所以 Chrome 已开 1 个窗口、快照有 3 个窗口时**不会新开窗口**，直接进匹配 → 两个目标匹配到同一个窗口（叠加 D3 第一条）。这就是 R 评审 R1-4 要求定义 `reuse_policy` 的地方，代码用"总是复用"给出了默认值，但没有写进任何文档。

### D4（P1）`verify` 只比位置、不比尺寸

`verify` 返回 `max(|dx|,|dy|)`（`restore/mod.rs:409-421`），宽高完全不校验。跨 DPI、任务栏位置变化、窗口有最小尺寸约束时，会出现"位置对、尺寸错"仍判 Success。建议改为四边偏差 + 尺寸偏差分别判定，并把阈值写成 `max(8, 2×scale)`（呼应 R 评审 R2-3）。

### D5（P1）恢复报告不落盘，"可诊断"卖点目前不成立

`restore_apply` 返回 `RestoreReport`，前端存在 `useState` 里（`Restore.tsx:41`）。关窗、刷新、切换快照后报告即丢；进程崩溃后更没有。R 评审 R4 要求"异常退出后提供恢复提示"、§5.2 要求"最终结果可 `restore_get_report` 拉取"——**这两条现在一条都没落地，而且没有任何地方在写 `restore_runs`**。建议先落最小版：每次 run 写 `runs/run-*.json`（复用现有文件存储），列表页可回看最近 20 次。

### D6（P2）恢复串行 + 每应用最多等 8s，且不可取消

`wait_for_process_window` 每应用最多 8000ms（`restore/mod.rs:20, 432-451`），串行。10 个应用全未启动时最坏 ~80s，与 R 评审 R8 的"≤30s"直接冲突；UI 没有取消按钮（`Restore.tsx`）。至少加"取消"（`AtomicBool` 检查点）与并发上限（R 评审 §5.1 的固定流水线）。

### D7（P2）`z_order` 语义未定义，靠数组下标兜住

`WindowInfo` 没有 `zIndex` 字段（`models.rs:19-38`），`SceneWindow.z_order` 在 `save_scene` 里被赋成 `windows.len()`（`storage/mod.rs:100`）。当前因为数组顺序恰好等于 EnumWindows 顺序而"看起来对"，但一旦 UI 或存储对窗口做过滤/排序/分组，层序就静默错位。既然 R 评审已经指出"z_order 有字段无需求"，这里要么补需求 + 把 `z_index` 带进模型，要么删掉。

### D8（P2）并发写入期的工作区无法验证

截至本文写作，`pnpm build` 的 `tsc` 已通过（`@types/node` 是 15:56 之后补的），但 `vite build` 在本沙箱因 `esbuild spawn EPERM` 无法执行；`cargo test` 因无法下载 crates.io 依赖无法执行。也就是说：**这套代码从未被完整构建过一次**。在把评审结论当"已修"之前，先跑通 `cargo test`（`matcher.rs`/`layout.rs`/`filter.rs` 有 13 个单测）与 `pnpm build`。
